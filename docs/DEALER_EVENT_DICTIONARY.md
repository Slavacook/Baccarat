# Словарь событий дилера

## Статус документа

Этот документ фиксирует согласованный словарь событий дилера для:

- Godot-клиента;
- backend;
- Trainer Dashboard;
- live-log и live view.

Документ является источником правды для пользовательских названий событий и правил их показа.

## Главные правила

### 1. Пользователь не должен видеть технические event codes

Названия вроде:

- `winner_selection`
- `player_third`
- `banker_third`
- `fan_card_error`
- `payment_wrong`

не должны показываться в UI.

Пользователь должен видеть только нормальные русские формулировки.

### 2. Все названия и анонсы должны храниться на сервере

Frontend не должен сам придумывать финальные подписи событий.

Итоговый словарь событий, их категории, тексты и правила показа должны храниться на сервере и приходить в dashboard в нормализованном виде.

Временный frontend mapping допустим только как переходный слой, но не как постоянный источник правды.

### 3. Live-log показывает действия дилера, решения дилера и ошибки

Live-log должен показывать:

- действия дилера;
- решения дилера;
- ошибки дилера;
- короткие системные вехи, если они реально помогают читать ход раздачи.

Live-log не должен заранее показывать системные ожидания так, как будто это уже действие дилера.

### 4. Ожидания системы не показываются как действия дилера

Система может знать:

- кому по правилам положена третья карта;
- кто реально победил по правилам;
- какая сумма выплаты ожидается.

Но это знание системы не должно появляться в live-log как будто дилер уже это сделал или выбрал.

### 5. Имя дилера не повторяется в каждой строке live-log

Если открыт лог конкретного дилера, в каждой строке не нужно дублировать его имя.

Нужны короткие строки вида:

- `Отметил третью карту игроку`
- `Карта банкиру`
- `Выбрал маркер Игрока`
- `Ошибка: оплатил проигрышную ставку`

## Типы событий

События делятся на несколько смысловых типов.

### Действие дилера

Физическое или явное действие дилера:

- отметил чекбокс;
- снял чекбокс;
- собрал проигрышную ставку;
- оплатил выигравшую ставку.

### Решение дилера

Осознанный выбор дилера:

- выбрал, кому идёт третья карта;
- выбрал маркер победителя.

### Анонс

Короткая понятная формулировка подтверждённого решения:

- `Карта игроку`
- `Карта банкиру`
- `Карта каждому`
- `Победитель: Игрок`

Анонс можно показывать в live-log только если это уже подтверждённое действие или подтверждённый итог, а не скрытое ожидание системы.

### Ожидание системы

Внутреннее знание системы:

- кому положена третья карта;
- кто реально победил по правилам до выбора дилера;
- какая сумма должна быть выплачена.

Ожидания системы можно хранить и использовать на сервере, но нельзя показывать заранее как действия дилера.

### Ошибка

Неверное действие дилера:

- забрал выигрышную ставку;
- оплатил проигрышную ставку;
- ошибся в сумме оплаты;
- выбрал неверный маркер;
- выбрал неверную третью карту.

## События третьих карт

### События кликов по чекбоксам

Эти события логируются отдельно.

- `Отметил третью карту игроку`
- `Снял отметку третьей карты игроку`
- `Отметил третью карту банкиру`
- `Снял отметку третьей карты банкиру`

Это именно действия дилера в UI.

### Подтверждённые решения по третьим картам

Это не технические коды, а пользовательские названия подтверждённого решения:

- `Карта игроку`
- `Карта банкиру`
- `Карта каждому`

### Что не нужно показывать отдельным событием

Отдельное событие:

- `Без третьей карты`

не нужно.

Если система определила, что третья карта никому не нужна, это остаётся внутренним состоянием системы, а не отдельным пользовательским событием live-log.

## События маркеров победителя

### Клики по маркерам

Нужно логировать отдельные действия выбора и снятия:

- `Выбрал маркер Игрока`
- `Отменил маркер Игрока`
- `Выбрал маркер Банкира`
- `Отменил маркер Банкира`
- `Выбрал маркер Эгалите`
- `Отменил маркер Эгалите`

### Важное правило

Если дилер выбрал новый маркер, а предыдущий снялся автоматически, автоматическое снятие старого маркера не должно логироваться как отдельное действие дилера.

Логируется только то, что дилер действительно нажал сам.

## Решения по победителю

После подтверждённого выбора победителя должны использоваться нормальные формулировки:

- `Победитель: Игрок`
- `Победитель: Банкир`
- `Победитель: Эгалите`

Это уже не технический `winner_selection`, а пользовательский итоговый анонс.

## Сбор и оплата ставок

### Действия дилера

Нужны отдельные пользовательские события:

- `Собрал проигравшую ставку`
- `Оплатил выигравшую ставку`

Если в раунде таких действий несколько, лог показывает каждое фактическое действие отдельно.

### Ошибки

Нужны отдельные ошибки с понятными названиями:

- `Ошибка: забрал выигрышную ставку`
- `Ошибка: оплатил проигрышную ставку`
- `Ошибка: сумма оплаты неверна`

Если возможно, ошибка должна содержать пояснение, что ожидалось на самом деле.

Пример:

- `Ошибка: сумма оплаты неверна. Ожидалось: 1500`
- `Ошибка: оплатил проигрышную ставку. Ожидалось: собрать ставку`

## Формат ошибок

Ошибки должны быть короткими и понятными.

Базовый формат:

- `Ошибка: <что сделал не так>`

Если есть полезное ожидаемое действие или ожидаемое значение, добавляется уточнение:

- `Ожидалось: <правильное действие>`
- `Ожидалось: <правильная сумма>`

Примеры:

- `Ошибка: выбрал неверный маркер. Ожидалось: Банкир`
- `Ошибка: карта игроку. Ожидалось: карта банкиру`
- `Ошибка: сумма оплаты неверна. Ожидалось: 500`

## Что live-log должен показывать

Live-log должен показывать:

- действия дилера;
- решения дилера;
- подтверждённые анонсы;
- ошибки;
- короткие системные вехи вроде начала и завершения раздачи, если они помогают читать поток событий.

## Что live-log не должен показывать

Live-log не должен показывать:

- технические event codes;
- внутренние поля payload;
- ожидания системы как будто это уже выбор дилера;
- повтор имени дилера в каждой строке;
- лишние системные детали, которые не помогают тренеру читать действия дилера.

## Рекомендуемая структура server-side event object

Ниже желаемая структура нормализованного события, которое сервер хранит и отдаёт dashboard.

```json
{
  "event_code": "winner_marker_selected_player",
  "category": "dealer_decision",
  "visibility": "live_log",
  "label": "Выбрал маркер Игрока",
  "details": null,
  "expected_label": null,
  "round_number": 4,
  "dealer_id": 12,
  "dealer_name": "Иван",
  "session_id": 77,
  "created_at": "2026-04-29T10:15:30Z"
}
```

### Поля

- `event_code`
  - внутренний стабильный код события;
  - не показывается пользователю напрямую.

- `category`
  - тип события:
    - `dealer_action`
    - `dealer_decision`
    - `dealer_announcement`
    - `dealer_error`
    - `system_state`
    - `system_expectation`

- `visibility`
  - где событие должно показываться:
    - `live_log`
    - `live_table`
    - `round_summary`
    - `hidden`

- `label`
  - готовая русская строка для UI.

- `details`
  - дополнительное пояснение, если нужно.

- `expected_label`
  - строка для формата `Ожидалось: ...`, если у ошибки есть ожидаемый правильный вариант.

- `round_number`
  - номер раздачи.

- `dealer_id`
  - идентификатор дилера.

- `dealer_name`
  - имя дилера.
  - может использоваться в общих списках, но не должно повторяться в каждой строке лога конкретного дилера.

- `session_id`
  - идентификатор live-сессии.

- `created_at`
  - серверное время события.

## Минимальный обязательный набор пользовательских событий

### Третьи карты

- `Отметил третью карту игроку`
- `Снял отметку третьей карты игроку`
- `Отметил третью карту банкиру`
- `Снял отметку третьей карты банкиру`
- `Карта игроку`
- `Карта банкиру`
- `Карта каждому`

### Маркеры победителя

- `Выбрал маркер Игрока`
- `Отменил маркер Игрока`
- `Выбрал маркер Банкира`
- `Отменил маркер Банкира`
- `Выбрал маркер Эгалите`
- `Отменил маркер Эгалите`

### Итог победителя

- `Победитель: Игрок`
- `Победитель: Банкир`
- `Победитель: Эгалите`

### Работа со ставками

- `Собрал проигравшую ставку`
- `Оплатил выигравшую ставку`

### Ошибки

- `Ошибка: забрал выигрышную ставку`
- `Ошибка: оплатил проигрышную ставку`
- `Ошибка: сумма оплаты неверна`

## Правило внедрения

При дальнейшей реализации:

1. сначала сервер должен стать источником правды для словаря событий;
2. затем dashboard должен перестать показывать technical names;
3. затем Godot должен начать отправлять недостающие события кликов и решений;
4. только после этого можно убирать временные frontend mapping-слои.
