# DEALER EVENT DICTIONARY — Baccarat Trainer

## 1. Цель документа

Этот документ фиксирует единый словарь событий дилера для Baccarat Trainer.

Он нужен, чтобы Godot, backend и dashboard одинаково понимали:

- что именно сделал дилер;
- какое действие было правильным;
- где была ошибка;
- какую фразу должен видеть тренер в live-log;
- какую фразу можно использовать как анонс;
- какие значения сервер должен хранить для проверки и обучения.

Главная идея:

> В интерфейсе тренера не должно быть технических названий вроде `winner_selection`, `player_third`, `banker_third`, `fan_card_error`, `payment_correct`.
> Пользователь должен видеть только нормальные русские формулировки.

---

## 2. Главные правила

### 2.1. Технические event codes не показываются пользователю

Коды вроде:

- `winner_selection`
- `player_third`
- `banker_third`
- `fan_card_error`
- `payment_correct`
- `round_result`

могут жить внутри кода и payload, но не должны попадать в UI.

В UI должны быть только русские понятные формулировки.

### 2.2. UI показывает только русские формулировки

Trainer Dashboard и любой другой пользовательский интерфейс должны работать с готовыми русскими строками.

Примеры правильного вида:

- `Карта игроку`
- `Выбрал маркер Банкира`
- `Победитель: Эгалите`
- `Ошибка: оплатил проигрышную ставку на пару Банкира`

### 2.3. Live-log показывает действия дилера, решения дилера и ошибки

Live-log должен показывать:

- действия дилера;
- решения дилера;
- ошибки дилера;
- короткие системные события, если они действительно помогают читать ход раздачи.

Live-log не должен заранее показывать внутренние ожидания системы как будто это уже действие дилера.

### 2.4. Ожидания системы хранятся на сервере, но не показываются заранее как действия дилера

Система может заранее знать:

- кому положена третья карта;
- кто реально победил по правилам;
- какая сумма выплаты ожидается.

Эти данные нужны серверу для проверки, обучения и разбора ошибок, но live-log не должен показывать их заранее.

### 2.5. Логируем действия дилера, а не автоматические действия программы

В log должны попадать только осознанные действия дилера:

- нажал чекбокс;
- снял чекбокс;
- выбрал маркер;
- снял маркер;
- подтвердил решение;
- забрал ставку;
- оплатил ставку;
- сделал ошибочное действие.

Автоматические побочные эффекты UI не логируются.

### 2.6. Автоматическое снятие другого маркера не логируется

Если дилер выбрал один маркер, а предыдущий снялся автоматически, это автоматическое снятие не должно появляться в log.

Пример:

```text
Выбрал маркер Игрока
Выбрал маркер Банкира
```

Лишней строки:

```text
Отменил маркер Игрока
```

в этом случае быть не должно.

Если дилер сам повторно нажал на уже выбранный маркер, чтобы снять его, это уже отдельное действие, и его нужно логировать.

### 2.7. Имя дилера не повторяется в каждой строке live-log конкретного дилера

Если открыт лог конкретного дилера, каждая строка должна быть короткой.

Плохо:

```text
12:27:12 Славян #2 — winner_selection → Banker
```

Хорошо:

```text
12:27:12 Выбрал маркер Банкира
```

### 2.8. Все русские названия и анонсы должны храниться на сервере

Godot не должен сам придумывать финальные русские названия для dashboard.

Dashboard тоже не должен быть источником правды для словаря.

Источник правды должен быть на сервере:

- русские labels;
- категории событий;
- анонсы;
- правила показа в live-log;
- тексты ошибок;
- ожидаемые значения.

## 3. Термины

### 3.1. Действие дилера

Это то, что дилер реально сделал руками.

Примеры:

- `Отметил третью карту игроку`
- `Снял отметку третьей карты банкиру`
- `Выбрал маркер Банкира`
- `Забрал ставку на Игрока`
- `Оплатил ставку на Эгалите правильно: 22 350`

### 3.2. Решение дилера

Это подтверждённый итог выбора дилера после его действий.

Примеры:

- `Карта игроку`
- `Карта банкиру`
- `Карта каждому`
- `Победитель: Игрок`
- `Победитель: Банкир`
- `Победитель: Эгалите`

### 3.3. Анонс

Анонс — это фраза регламента, которую дилер должен произнести.

Важно:

> Анонс — это не категория события.
> Анонс — это отдельная фраза, которую можно связать с событием.

Пример:

- решение: `Карта каждому`
- анонс: `Карта каждому`

Анонсы должны храниться отдельно, чтобы их можно было менять в одном месте.

### 3.4. Ожидание системы

Это то, что сервер считает правильным по правилам.

Примеры:

- `Ожидалось: карта игроку`
- `Ожидалось: карта банкиру`
- `Ожидалось: карта каждому`
- `Ожидалось: Игрок`
- `Ожидалось: Банкир`
- `Ожидалось: Эгалите`
- `Ожидалось: 22 350`

Ожидания системы нужны для:

- проверки правильности действий;
- объяснения ошибок;
- будущих обучающих подсказок;
- режима разбора раздачи.

Они не должны заранее показываться в live-log как действия дилера.

### 3.5. Ошибка

Это ситуация, где действие дилера не совпало с правильным действием или правильным значением.

Примеры:

- `Ошибка: забрал выигрышную ставку на Игрока`
- `Ошибка: оплатил проигрышную ставку на Эгалите`
- `Ошибка: оплатил ставку на Эгалите: 23 350`
  `Ожидалось: 22 350`

## 4. Этапы раздачи

Используем такую последовательность:

```text
Новая раздача
→ карты открыты
→ если карта нужна: карта игроку / карта банкиру / карта каждому
→ если карта не нужна: сразу выбор победителя
→ выбор победителя
→ сбор проигрышных ставок
→ оплата сыгравших ставок
→ конец раздачи
```

Важно:

- не использовать формулировку `карты сданы`;
- использовать формулировку `карты открыты`;
- отдельное событие `Без третьей карты` не нужно.

## 8. Решение о третьих картах

Это итог после подтверждения.

Важно:

- если отмечен только игрок → решение `Карта игроку`;
- если отмечен только банкир → решение `Карта банкиру`;
- если отмечены игрок и банкир → решение `Карта каждому`;
- `Карта каждому` появляется только после подтверждения, если отмечены оба чекбокса;
- отдельной кнопки `Карта каждому` нет;
- отдельного события `Без третьей карты` не нужно.

## 15. Ожидания системы

Сервер может хранить:

- `Ожидалось: карта игроку`
- `Ожидалось: карта банкиру`
- `Ожидалось: карта каждому`
- `Ожидалось: Игрок`
- `Ожидалось: Банкир`
- `Ожидалось: Эгалите`
- `Ожидалось: {expected_amount}`

По умолчанию live-log не показывает ожидания заранее.

Ожидания должны использоваться:

- в деталях ошибки;
- в будущей обучающей подсказке;
- в режиме разбора раздачи.

---

## 16. Формат live-log

### 16.1. Без имени дилера

Если открыт log конкретного дилера, имя дилера в каждой строке не нужно.

### 16.2. Короткий формат

Пример:

```text
12:20:01 Новая раздача
12:20:06 Карты открыты
12:20:10 Отметил третью карту игроку
12:20:12 Отметил третью карту банкиру
12:20:14 Карта каждому
12:20:22 Выбрал маркер Эгалите
12:20:25 Победитель: Эгалите
12:21:03 Забрал ставку на Игрока
12:21:09 Оплатил ставку на Эгалите правильно: 22 350
```

### 16.3. Ошибка суммы

```text
12:23:42 Ошибка: оплатил ставку на Эгалите: 23 350
Ожидалось: 22 350
```

### 16.4. Ошибка типа ставки

```text
12:24:18 Ошибка: оплатил проигрышную ставку на пару Банкира
```

```text
12:25:41 Ошибка: забрал выигрышную ставку на Игрока
```

## 18. Где использовать словарь

### 18.1. Godot

Godot должен отправлять:

- `event_code`
- значения вроде `actual_value`, `selected_target`, `is_checked`
- `round_number`
- `dealer_id`
- `session_id`

Godot не должен сам придумывать русские названия для dashboard.

### 18.2. Backend

Backend должен:

- принимать события;
- проверять их по правилам;
- определять правильность;
- добавлять expected values;
- подставлять русские labels из словаря;
- отдавать dashboard уже нормализованные события.

### 18.3. Dashboard

Dashboard должен:

- показывать `dashboard_label`;
- показывать `expected_value`, если это ошибка;
- не показывать technical codes пользователю;
- не показывать имя дилера в логе конкретного дилера;
- не показывать system expectations заранее как действия дилера.

---

## 19. Что не делать

Не показывать в UI:

- `winner_selection`
- `player_third`
- `banker_third`
- `fan_card_error`
- `payment_correct`
- `round_result`

Не использовать технические стрелки вида:

- `winner_selection → Banker`
- `player_third → player_third`

Не показывать ожидания системы заранее как будто это действия дилера.

Не логировать автоматические снятия маркеров, если они произошли из-за выбора другого маркера.

Не добавлять событие `Без третьей карты`.
